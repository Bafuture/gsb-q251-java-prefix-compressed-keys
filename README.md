## 任务提示词

以下为本题完整的 User Prompt 原文，两次执行必须使用完全相同的文本。

我们的有序键有很长的公共前缀，直接存储浪费空间，按序遍历时又要解压。请从零实现一个前缀压缩键存储组件。仓库目前只有一个空的 Maven 工程（pom.xml 只声明 JUnit 5 与 AssertJ）。要求：1) 支持按键有序插入，写入时只保存与相邻键的公共前缀长度与剩余后缀；2) 支持按序遍历：遍历时必须能正确还原完整键并能定位到原始条目；3) 支持按键点查：查不到时给出可插入位置的提示；4) 支持删除后压缩信息重建：删除中间项时后续条目的前缀关系可能变化，必须保证仍能正确还原；5) 支持并发读写：读操作不阻塞，写入时只影响局部条目并保证读到的键要么是旧值要么是新值；6) 给出压缩率数据：与不压缩存储相比的空间占用对比（不同前缀长度下各给一组）；7) 提供统计：条目数、平均前缀长度、压缩后总字节数；8) 测试覆盖插入与遍历还原、点查、删除后重建、并发读写一致性与压缩率数据；`mvn -q verify` 一条命令跑通。

## 实现说明

核心类：`src/main/java/com/example/gsb/pfc/PrefixCompressedKeyMap.java`（泛型 `<V>`）

### 存储模型（front-coding / 前驱差分）

有序数组中每个条目只持久化：

- `prefixLen`：与**前驱键**最长公共前缀（LCP）长度（首项锚点为 0）；
- `suffix`：去掉公共前缀后的剩余字节（UTF-8）。

完整键还原为 `前驱键[0..prefixLen) + suffix`；锚点（`prefixLen == 0`）保存整条键。
按序遍历时从前到后增量拼接（O(总长度)），点查二分定位时按需沿前缀链回溯到锚点还原，
**不需要**额外存储任何完整键。

- 有序插入：二分找位置，只构造新节点并重算其后继一条元数据（后继与新前驱的 LCP），
  其余节点与旧快照共享；插入到表头时旧锚点转为普通节点。
- 点查：`lookup(key)` 返回 `found / index / value`；未命中时 `index` 即保持有序的
  可插入位置（`[0, size]`）。
- 删除：移走节点后只需重建其后继（对新前驱重算 LCP；删的是首项则后继成为新锚点），
  其他节点的前缀关系不变，直接复用。
- 并发：整表为不可变快照，经 `volatile` 发布。读完全无锁、不阻塞，任何遍历/点查都落在
  某一个一致快照上，读到的条目要么是旧值要么是新值，不会出现撕裂；写操作在 `synchronized`
  下做局部复制（copy-on-write），最多改动 2 个条目的压缩信息。

### 统计

`stats()` 返回：条目数、平均前缀长度、压缩后字节数、不压缩字节数（每项均为
`varint(长度)+内容`，LEB128 记账）、压缩比与节省比例。

实测（5000 个键，唯一尾部 12 字节，测试自动打印）：

| 公共前缀长度 | 压缩后(B) | 不压缩(B) | 压缩比 | 节省 |

| 0  | 56332 |  65000 | 1.15x | 13.3% |
| 8  | 56340 | 105000 | 1.86x | 46.3% |
| 16 | 56348 | 145000 | 2.57x | 61.1% |
| 24 | 56356 | 185000 | 3.28x | 69.5% |

### 测试覆盖（12 个用例）

- `PrefixCompressedKeyMapTest`：压缩元数据断言、乱序插入仍有序、遍历完整还原、
  点查命中/未命中与插入位置提示、重复键替换、删除中间项/首项/末项后重建、
  多轮删除重插、统计数据、空表与 null 防御。
- `ConcurrencyTest`：2 写 + 4 读并发 2s，校验快照内严格有序无重复、值恒为已发布版本、
  遍历与点查一致、最终状态完整。
- `CompressionBenchmarkTest`：6 种前缀长度的压缩率对比，断言压缩比随前缀长度单调上升。
